# 旧数据格式识别与映射规则

> 目标:把任意来源的 CSV / Excel 账单,映射成 gridly 的 5 张表。
> **只支持 CSV / Excel**。其它格式(其它 sqlite / JSON / 图片)不在本 skill 范围,遇到时明确告知用户。

---

## 1. 常见来源特征速查

先看表头判断来源,再定映射。**不要假设列名** —— 每个 app 导出格式都不同,必须实际读表头。

| 来源 | 典型表头 | 特征 |
|---|---|---|
| 支付宝账单 | `交易时间` `交易分类` `交易对方` `商品说明` `收/支` `金额` `收/付款方式` `交易状态` | **有「收/支」独立列**;金额恒正;开头有几行说明文字;末尾有汇总行 |
| 微信账单 | `交易时间` `交易类型` `交易对方` `商品` `收/支` `金额(元)` `支付方式` `当前状态` | 结构同支付宝;「收/支」是 `收入` / `支出` / **`不计收支`**;**没有「交易分类」列** |
| 随手记 | `日期` `类别` `账户` `金额` `备注` | 金额**带符号**(支出为负);账户是账户组+明细 |
| MoneyManager | `date` `type` `category` `account` `amount` `note` | 金额带符号;`type` 是 `INCOME`/`EXPENSE`/`TRANSFER` |
| 挖财 | `交易日期` `交易类型` `分类` `账户` `金额` `备注` | 中文表头;类型含「支出/收入/转出/转入/借出/借入」 |
| 银行流水 | `交易日期` `摘要` `借方发生额` `贷方发生额` `余额` | **双金额列**(借/贷),一列有值一列空;无分类 |
| 通用 Excel | 任意 | 必须逐列判断语义 |

> 支付宝/微信导出的 CSV 前几行是说明文字,**表头不在第 1 行**。必须先定位表头行。

> ### ⚠️ 微信账单没有「交易分类」列
>
> 这是微信和支付宝最大的结构差异,也是最常见的翻车点:
> - **支付宝**有 `交易分类`(餐饮/交通/…)→ 直接当分类
> - **微信**没有分类列,只有 `商品`(火锅/外套/猫粮)和 `交易类型`(商户消费/转账)
> - `商品` 才是分类来源;`交易类型` 太粗(只有 商户消费/转账),拿它当分类会把工资记成消费
> - `商品` 的值很细,脚本会用关键词表归并回系统 23 条(火锅→餐饮、外套→购物、猫粮→宠物…)
> - **不要**用 `交易对方`(海底捞/优衣库)当分类 —— 那是商户名,不是消费类别
>
> 脚本已内置 `商品` → 分类的识别和关键词归并,正常情况下**不需要写 config**。
> 若某个账单仍全被跳过(通常报「分类为空」),说明分类列没识别出来,此时用
> `--config` 显式指定 `"category": "<该列的表头文字>"`。
>
> **自检陷阱**:0 行数据时脚本的所有自检项都会「通过」(没有悬空引用,因为没有行)。
> 所以**必须看脚本输出的「流水写入 N 笔」** —— N=0 就是全被跳过了,不能只看「自检全过」。

## 2. 五步识别流程

### Step 1 — 定位表头行
- 逐行读前 30 行,找**字段数最多且含已知关键词**(时间/日期/金额/类型)的那一行
- 支付宝/微信:`交易时间` 出现的那行
- 记录表头行号,数据从下一行开始

### Step 2 — 判定数据行边界
- 扫描直到**汇总/统计行**(含「合计」「总计」「共 N 笔」等字样)或空行
- 汇总行**不迁移**

### Step 3 — 逐列定语义
对每个表头列,判定它属于哪一类:

| 语义类 | gridly 目标 | 常见列名 |
|---|---|---|
| `date` | `transactions.occurred_at` | 交易时间 / 日期 / 交易日期 / date / 时间 |
| `amount` | `transactions.amount`(取绝对值) | 金额 / 发生额 / amount |
| `direction` | 决定 `transactions.type` | 收/支 / 交易方向 / type / 借贷标志 |
| `category` | `transactions.category_id` | 交易分类 / 类别 / 分类 / category / 摘要 |
| `account` | `transactions.account_id` | 账户 / 支付方式 / 收/付款方式 / 账号 / account |
| `dest_account` | `transactions.destination_account_id` | 对方账户 / 转出账户 / 转入账户 / 转户账户 |
| `note` | `transactions.note` | 备注 / 商品说明 / 商品 / note / 摘要 |
| `balance` | `assets.initial_balance` | 余额 / 当前余额 / balance |
| `ignore` | 丢弃 | 交易对方 / 交易状态 / 当前状态 / 编号 / 商家订单号 |

> **「摘要」列有歧义**:银行流水里它是描述(→ note),部分记账 app 里它是分类(→ category)。
> 看内容判断:内容是「餐饮」「购物」这类词 → 分类;是「超市购物 20.5」这类描述 → 备注。

### Step 4 — 判定类型映射
`direction` 列的取值 → gridly `transactions.type`:

| 旧值 | gridly type |
|---|---|
| 支出 / EXPENSE / 付款 / 借 | `expense` |
| 收入 / INCOME / 收款 / 贷 | `income` |
| 转账 / TRANSFER / 转出 / 转入 / 余额变更 | `balance` |
| 借出 /  lend_out | `lend_out` |
| 借入 / borrow_in | `borrow_in` |

若**没有** direction 列,靠金额符号:负数 → `expense`,正数 → `income`。
符号和 direction 冲突时,**以 direction 为准**,并记入报告。

### Step 5 — 判定账户与分类
见 §3、§4。

## 3. 账户映射规则

### 3.1 资产 vs 账户组
有些 app 有「账户组 → 账户明细」两级(随手记)。
gridly 只有一层 `assets`,所以**用明细账户名**,组名作为前缀会更清晰:
- 旧:`现金` / `招行储蓄卡` → 新:`现金` / `招行储蓄卡`
- 旧组 `现金` 下有 `零钱` / `余额` → 新:`现金-零钱` / `现金-余额`

### 3.2 段位判定

| 旧数据线索 | `assets.type` | 附加 flag |
|---|---|---|
| 现金 / 储蓄卡 / 借记卡 / 零钱 / 微信 / 支付宝 | `cash_flow` | `include_in_transactions=1` |
| 余额宝 / 基金 / 股票 / 理财 / 证券 | `investment` | `include_in_transactions=0` |
| 公积金 / 社保 / 医保 / 年金 | `benefit` | `include_in_transactions=0` |
| 信用卡 / 花呗 / 白条 / 房贷 / 车贷 / 欠款 | `receivable` | `act_as_cash_flow=1`(可消费类)/ `is_lender=0` |
| 借给别人 / 应收 / 别人欠我 | `receivable` | `is_lender=1` |
| 房 / 车 / 房产 / 车辆 | `fixed_asset` | `include_in_transactions=0` |
| 其它 / 未分类 | `other` | `include_in_transactions=0` |

> **余额为负的账户**:通常是负债(信用卡欠款)。归 `receivable` + `is_lender=0`,
> 余额取绝对值放进 `initial_balance`,靠 `type='balance'` 的还款流水体现减少。
> 拿不准就保留原符号,记入报告让用户确认。

### 3.3 余额语义(最容易错的地方)

gridly 的 `initial_balance` 是**期初余额**:
```
currentBalance = initial_balance
               + Σ(income) - Σ(expense)
               - Σ(balance 源账户) + Σ(balance 目标账户)
               + Σ(lend_out) - Σ(borrow_in)
```

旧数据给的「余额」通常是**当前余额**。两种处理:

| 旧数据 | 处理 |
|---|---|
| 只给当前余额,无流水 | 直接填 `initial_balance`(无流水可叠加,等价) |
| 给当前余额**且**有流水 | **`initial_balance = 当前余额 − 由流水推导的净变动`**,否则余额会重复计算 |
| 只给期初余额(导出项明写「期初」) | 直接填 `initial_balance` |

> 推荐做法:**先按流水算出净变动,再倒推期初余额**。这样导入后 app 里显示的当前余额
> 与旧 app 一致 —— 这是用户判断迁移是否成功的首要标准。

## 4. 分类映射规则

### 4.1 优先复用系统分类
旧分类名命中系统 23 条 → 直接用系统分类 id。命中判定:
- **完全相等**(最稳)
- 去掉空格/全半角差异后相等
- 常见别名表见下

| 旧名 | → 系统分类 |
|---|---|
| 餐饮 / 吃饭 / 餐厅 / 食物 | 餐饮 |
| 交通 / 打车 / 公交 / 地铁 | 交通 |
| 购物 / 淘宝 / 京东 / 网购 | 购物 |
| 房租 / 房贷 / 水电 | 居住 |
| 话费 / 流量 / 通讯费 | 通讯 |
| 看病 / 医院 / 药品 | 医疗 |
| 学费 / 培训 / 书籍 | 教育 |
| 电影 / 游戏 / 娱乐 | 娱乐 |
| 家具 / 家居 | 居家 |
| 化妆品 / 美容 / 护肤 | 美妆 |
| 宠物 | 宠物 |
| 工资 / 薪水 | 工资 |
| 年终奖 / 绩效 | 奖金 |
| 利息 / 收益 | 理财 |
| 副业 / 外快 | 兼职 |
| 退款 / 退货 | 退款 |

> **别名表只是提示,不是硬规则**。最终以用户数据里出现的实际分类名为准,先统计全部唯一分类名再决定。

### 4.2 新建自定义分类
未命中的 → 新建,`is_system = 0`:
- `type`:按旧分类的收支方向定(`expense` / `income`)。
  - 若该分类在旧数据里**只出现在支出行** → `expense`
  - **只出现在收入行** → `income`
  - **两种都有** → 按出现次数多的那种,另一方向的行记入报告
- `color`:从 `hash_palette` 12 色里取(见 `seed_data.json`),按分类名 hash 分散,避免全灰
- `icon`:从 `seed_data.json` 的 `icon_map_keys` 里挑语义相近的;挑不到用 `more_horiz`
- `sort_order`:递增值(100、101、102…)

### 4.3 特殊归类
- 旧分类叫「投资」「基金」「股票」且行是资金划转 → 归到 `cat.type='investment'`
  (这样这些行**不计入月度收支**,符合用户预期)
- 旧分类叫「还款」「还信用卡」→ 归 `cat.type='liability'`
  (app 报表会把这类 `balance` 流水算作支出,见 target-schema §5.4)

## 5. 金额与日期解析

### 5.1 金额
- 去货币符号(¥ $ ¥)、去千分位逗号、去中文「元」
- 括号表示负数:`(50.00)` → `-50.00`
- 写入 gridly 一律 **取绝对值**,方向由 `type` 表达
- 保留 2 位小数(`round(x, 2)`)
- 解析失败的行 → 记入报告,不迁移

### 5.2 日期 → epoch 秒

**这是整个迁移最容易出错的地方。** drift 存的是 **Unix epoch 秒**,且 app 的流水日期
在真实数据里表现为**本地时区午夜**(UTC+8 是 `00:00:00`)。

| 旧数据日期形态 | 处理 |
|---|---|
| `2026-01-15` | 当天**本地午夜** → epoch 秒 |
| `2026/01/15 14:30:00` | 保留时分秒 |
| `20260115` | `YYYYMMDD` → 本地午夜 |
| `2026年1月15日` | 本地午夜 |
| Excel 序列号(如 `46037`) | Excel 基准 1899-12-30,加天数后取本地午夜 |

计算方式(用系统本地时区,不要硬编码 UTC+8):
```python
import datetime
dt = datetime.datetime(2026, 1, 15)          # naive = 本地时区
epoch = int(dt.timestamp())                  # 本地午夜对应的 epoch 秒
```

> ⚠️ **绝对不要**写 `int(dt.timestamp() * 1000)`(毫秒)→ app 会显示「58792 年」。
> 也**不要**用 `datetime.utcfromtimestamp()` 解读用户给的日期。

### 5.3 时区一致性
整个迁移用**同一个时区**处理所有行(系统本地时区)。若用户数据里带时区后缀(如 `+08:00`),按它解析。

## 6. 记录「无法迁移」的判定

以下情况**不要硬凑**,全部记入报告:

| 情况 | 处理 |
|---|---|
| 日期解析失败 | 跳过,记录原行 |
| 金额解析失败 | 跳过,记录原行 |
| 类型无法判定(既无 direction 也无符号) | 跳过,记录原行 |
| 转账只有一端(缺源或缺目标) | 跳过,记录原行 |
| 转账两端账户名在源数据里找不到 | 跳过,记录原行 |
| 分类方向矛盾(同一分类既有支出又有收入,且次数接近) | 归多数方向,记录矛盾次数 |
| 账户余额与流水推导值差异过大(>1 元) | 按流水推导,记录差异 |
| 汇总行 / 说明行 | 跳过(不记录,正常) |
| 完全重复的行 | 保留全部(除非能确认是导出重复),记录疑似重复数 |

报告由脚本自动生成,格式见 `scripts/build_migrated_db.py` 的 `write_report()`。

## 7. config.json 格式

全部字段可选。**只在自动识别不准时才需要**。

```json
{
  "header_row": 6,
  "columns": {
    "date": "交易时间",
    "amount": "金额",
    "direction": "收/支",
    "category": "交易分类",
    "account": "收/付款方式",
    "dest_account": "转入账户",
    "counterparty": "交易对方",
    "note": "商品说明",
    "balance": "余额"
  },
  "account_types": {
    "花呗": "receivable",
    "余额宝": "investment",
    "公积金": "benefit"
  },
  "category_aliases": {
    "吃饭": "餐饮",
    "打车": "交通"
  },
  "skip_rows_before": 0,
  "skip_rows_after": 0,
  "default_account": "现金",
  "degrade_transfers": false
}
```

| 字段 | 作用 |
|---|---|
| `header_row` | 表头在第几行(1-based)。不填则自动检测 |
| `columns` | 语义 → 表头文字。**列名要跟源文件完全一致**(去掉首尾空格) |
| `account_types` | 账户名 → gridly 资产段位。合法值:`cash_flow` `investment` `benefit` `receivable` `fixed_asset` `other` |
| `category_aliases` | 旧分类名 → gridly 分类名。映射到的名字必须是系统 23 条之一 |
| `skip_rows_before` | 跳过前 N 行数据(不含表头行) |
| `skip_rows_after` | 跳过末尾 N 行(汇总区) |
| `default_account` | 流水没有账户列时用哪个账户兜底,默认「现金」 |
| `degrade_transfers` | 转账推不出目标账户时:`false`(默认)= 不迁,列入报告;`true` = 降级成普通收支写入 |

**`columns` 可用的语义键**:`date` `amount` `direction` `category` `account` `dest_account` `counterparty` `note` `balance`

> 指定的列如果表头里找不到,会被静默忽略 —— 跑完看脚本输出的「识别到的列语义」确认生效了。

## 7.5 转账类行怎么处理(重要)

微信/支付宝把「自己账户之间互转」标成 **「不计收支」**。这类行的特征:
- 有金额,但**没有**对端账户信息(CSV 只给「支付方式」= 发起方)
- 方向本身有歧义:「当前状态=已存入零钱」像转**进**,「商品=还钱」字面像转**出**,两种解读对余额的影响正好相反

gridly 的调拨(`type='balance'`)必须 `account_id` + `destination_account_id` **成对**。
猜一个方向的后果:
- 记 `balance` + `dest=NULL` → 余额公式照扣,凭空断言"钱出去了"
- 记 `expense` → 首页口径(`type!='income'` 全算支出)凭空多一笔支出,报表口径又不认,首页和报表打架

**所以默认不迁**,列入报告让用户决定补录方式(报告里会写清原始行 + 歧义分析 + 补录指引)。

想保留这条数据(降级成普通收支),config 里加 `"degrade_transfers": true`:
- 还款类(分类含「还/还款/还贷/信用卡」)→ 降级为 `expense`
- 其它 → 降级为 `income`

> 旧数据里**有**对端账户列时,应该映射到 `dest_account`,这样能正确建成 `balance` 调拨,不用降级。
> 脚本会自动尝试:`dest_account` 列 → 「交易对方」列(若恰好是已知账户名)。

## 8. 收/支方向映射补充

| 旧值 | gridly `transactions.type` |
|---|---|
| 支出 / EXPENSE / 付款 / 借 / 消费 | `expense` |
| 收入 / INCOME / 收款 / 贷 / 入账 | `income` |
| 转账 / TRANSFER / 转出 / 转入 / 余额变更 / **不计收支** | `balance` |
| 借出 / lend_out | `lend_out` |
| 借入 / borrow_in | `borrow_in` |

> **「不计收支」是支付宝/微信的标准值**,表示钱在账户间流转 → `balance`。
>
> 没有 direction 列时靠金额符号:负数 → `expense`,正数 → `income`。
> 符号和 direction 冲突时**以 direction 为准**。
