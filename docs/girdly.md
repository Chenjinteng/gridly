# Gridly 动画流畅度专项审计与优化

你正在维护 Gridly 项目，这是一个基于 Flutter 3、Riverpod、Drift 和 go_router 的本地优先记账 App，主要交付平台为 Android。

项目已有 docs/UI_UX.md、docs/DEV.md 和设计规范。必须先读取这些文档，并遵循现有架构和设计决策。

## 本次目标

解决 Gridly 中动画不够丝滑的问题。

重点不是增加动画，而是识别并修复以下问题：

* 手势跟随迟滞。
* 松手后动画不自然。
* 页面切换突兀。
* 列表更新跳动。
* 动画期间 Widget 重建或状态竞争。
* UI / Raster 帧耗时过长。
* 动画曲线、距离和时长不匹配。

## 第一阶段：代码审计，不修改文件

优先阅读以下模块：

1. lib/features/ledger/：流水列表、滑动删除和列表更新。
2. lib/features/shell/：底部五 Tab 容器与页面保活。
3. lib/features/add/：金额输入、计算器、日期选择和 SaveBar。
4. lib/features/stats/：图表与月份切换。
5. lib/core/router/：go_router 路由和页面转场。
6. lib/core/theme/：已有视觉规范及主题配置。

实际文件名以仓库为准，不得假设目录中一定存在某个文件。

检查 AnimationController、CurvedAnimation、GestureDetector、Transform、AnimatedSwitcher、AnimatedList、ListView、CustomPainter 等相关实现。

重点分析：

* 是否在高频手势回调中触发过大的 Widget 子树重建。
* AnimationController 是否正确管理生命周期。
* 手势拖动和释放后的动画是否使用连续的位移与速度。
* 是否存在重复启动、取消不及时、状态竞争或动画残留。
* 列表删除时是否协调了动画、数据更新和 Widget 移除。
* 页面切换是否叠加了路由动画与组件入场动画。
* 是否存在昂贵的布局、绘制、阴影、裁剪或离屏渲染。
* Riverpod 状态更新是否导致无关区域重复构建。
* 是否有动画在页面不可见时仍持续运行。

每个问题必须提供具体文件、代码位置、问题机制和判断依据。

如果只是潜在风险而没有复现证据，应明确标记为待验证。

## 第二阶段：优先优化滑动删除

先分析当前自定义滑动删除实现，不要直接换成第三方库。

分别评估：

A. 手指拖动阶段：
位移是否直接跟随手势，是否存在多余的动画插值或延迟。

B. 松手阶段：
是否正确处理速度、阈值、取消手势、吸附目标和动画反向。

C. 删除阶段：
记录退出、相邻项目补位、数据更新和 Widget 生命周期是否连贯。

D. 连续交互：
快速滑动多条记录、反向拖动、动画中再次触摸、列表刷新时是否出现异常。

只有发现明确问题后才修改实现。

## 第三阶段：性能验证

指导我使用 Flutter DevTools 在 profile 模式下复现和分析问题。

优先采集：

* 滑动删除时的 UI / Raster 帧耗时。
* 页面切换时的慢帧。
* 列表动画期间的 Widget build、layout 和 paint 事件。
* 首次播放动画与重复播放的差异。

如果没有实际设备、运行环境或性能数据，不得声称已完成性能验证。

## 第四阶段：实施与验收

按风险最低的顺序进行小批量修改。

优先修复：

1. 明确的状态竞争与动画中断问题。
2. 高频手势路径中的不必要工作。
3. 列表删除与重排的不连续。
4. 路由与组件动画的重复叠加。
5. 有实际证据支持的绘制性能问题。

保留现有业务逻辑、设计 Token 和本地数据库行为。

不要为了追求动画效果引入新的依赖，除非有明确的技术依据。

完成后执行适用的 Flutter analyze、测试和构建检查，并报告：

* 修改的文件。
* 修复的问题及原因。
* 修改前后的行为差异。
* 已执行的测试和实际结果。
* 仍需在 Android 真机验证的内容。

本轮先输出审计报告和修改计划，等待确认后再开始修改代码。
